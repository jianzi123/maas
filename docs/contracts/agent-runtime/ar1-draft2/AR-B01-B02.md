# AR-1 1.0.0-draft.2：创建查回与调用数边界

本补充仅收敛Mika评论01a1f1ee-589e-77a7-8058-ba9e496237fc的AR-B01/B02，合并原后端01a1f1ea-6da3-74bf-8611-2ee40b3820c7和前端01a1f1ec-6b56-7296-a387-99993d8a804e意见。原draft.1与ZIP按字节保留；本包给出独立draft.2 OpenAPI、事件Schema及差异，不覆盖原件。其余AR-1实现继续原MAAS-20/5，状态仍待产品/独立QA验证。

## AR-B01：创建前即知的命令身份

新增管理会话只读GET `/api/agent/v1/session-creation-commands/{operation_id}`。operation_id就是原ConversationCreate.client_operation_id，不需要session_id。复用原`__Host-maas_session`可信认证与当前权限；不接受owner/principal/hash覆盖参数，不使用平台推理Key登录。

创建命令唯一键为(可信授权域、稳定principal ID、create-session操作域、client_operation_id)，不是易变的登录Cookie/session ID。普通Run的幂等键仍在已知会话作用域，两者不互相解析。创建入参Schema不变。服务器用已固定Canonical JSON规则对title/model_alias等创建载荷计算hash；重复键拒绝，文本不偷偷trim/Unicode改写。key与规范hash及新Session必须在同一主库事务提交，不能先返回session_id后异步建命令映射。

| 场景 | 规范结果与允许行为 |
|---|---|
| 首次创建提交成功 | 原POST 201 Conversation，保存永久关联原ID；提交ACK丢失先查本新GET |
| 同principal、同操作域、同key、同hash | 原POST可200返回同一仍存在的Session；不得插入第二个Session。UI刷新/恢复流程仍只GET，不自动POST |
| 同key异hash | POST 409 operation_conflict且无修改；不能覆盖旧hash/旧Session或偷偷换ID |
| GET 200 | SessionCreationCommand：client_operation_id、原session_id、state=accepted、原request_sha256；之后GET原Session快照。仅证明原创建已提交，不证明当前对象仍存在或任何Run可调用 |
| GET 404 not_found | 当前principal下没有可读的权威保留结果，创建结果未知；不等于“未执行”。不扫标题/列表/最近Session，不换key、不自动POST |
| GET 503 dependency_unavailable | 主库/命令读取不可用或证据无法确认，结果未知；保留原key，按原只读退避重查 |
| 未认证/越权 | 401/403按现有会话权限；其他主体的操作ID不泄露结果，通用404。相同UUID可在不同principal域独立使用，不能返回对方行 |
| 原Session已逻辑删除 | GET命令仍指原session_id；Session GET按原删除语义404，不能重新创建或选同名对象。重复创建POST若不能返回原存活Session则409 state_conflict，不复活它 |
| 已按批准策略清理的命令 | 有墓碑则410，结果保留未知/人工核对，不自动重用ID。无批准保留策略不清理；不在本补充编造TTL |

新GET不比较请求hash，也不产生409写冲突；hash比较只在创建POST处理，GET返回保存的原hash供核对。新的SessionCreationCommand独立于原会话内Command，不给后者添加nullable session_id或另造unknown=200的虚假成功。现有Error结构不变，404/503示例仅验证body形状，不宣称实际HTTP已发生；其retryable仅允许读重试。

副作用核验：创建ACK丢失→浏览器刷新→新GET原operation_id→原Session快照，应观察新增创建POST=0、第二Session=0；数据库断开/不同主体/删除后的原映射各独立取证。首期接缝P2，完整创建刷新恢复验收前P1，闭合由MAAS-20实现、MAAS-5消费、MAAS-7独立验证。

## AR-B02：可完整投影的显式调用数

`RunLimits.max_model_calls`线格式从1..1,000,000收敛为1..10,000，无default。`RunCreate`与`Run`同时约束：mode=chat时max_model_calls必须等于1，不能只在文案或前端限制。`Run.child_request_ids.maxItems=10000`原值保留，不增加分页或截断能力。

服务端接收顺序：认证/原命令幂等核验 → 请求Schema（1..10000及chat=1）→ 当前明确安装策略/能力与预算校验 → 同事务创建Run等写入。已存在同key同hash的原命令仍按原恢复规则返回原身份，不再次建Run/模型请求。

对新命令，allowed_max=min(10000, 安装明确model-call上限, Chat模式上限1)。请求须1≤requested≤allowed_max，否则拒绝；wire/Chat边界非法400 invalid_request，合法wire但超过较小安装策略422 run_limit_exceeded。安装策略必须显式配置；10,000只是响应容量上界，不是默认运行额度、预算或性能承诺。不得先把10001裁为10/10000后接受，也不静默改变用户提交的max_model_calls；用户确认较小值后用新意图提交。

例如：agent请求10000、安装上限10000可接受；请求10001、安装10也必须拒绝；请求10、安装5返回422；Chat请求2即使安装10000仍400，Chat请求1可再检查原平台Key预算/其他Run限制。

每个新模型调用前检查已分配的稳定model_call_id/子request关联数，不只统计成功次数；已开始、失败、在途或未知提交都不能无成本穿过调用次数限制。恢复查询不增加调用计数；同一原身份去重不另占次数。达到accepted cap后无下一child dispatch，沿原limit_reached规则；父Run不扣第二份请求/Token/金额预算。

Run GET/快照/事件必须完整保留原child_request_ids，包括10000边界；只读分页steps/tool-calls不替代完整原子关联。发现持久数据超出本版可完整表示边界时返回503/数据需核对，不能截断或改旧终态/消费；若已有旧版本非合规数据，由原后端显式迁移/原版本读取处理，不在本轮假设已有这类真实数据。更大规模后续另列分页协议及版本。

## 字段与版本对照

| 位置 | draft.2最小变化 |

| OpenAPI info.version | 1.0.0-draft.1→1.0.0-draft.2 |

新消费者要支持新GET和更严格cap，不能用探测性POST测试端点是否存在；旧服务新GET 404仍为创建恢复未知。既有Cookie/CSRF、工具能力/票据、终态/观测、审批/fence/未知占用均不改。新版本静态例中只将原Chat cap3改为1；旧37样例与64检查仍按原draft.1留档，不覆盖成新通过数。
