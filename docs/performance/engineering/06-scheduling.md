# 容量约束下的连续批处理与公平性

可运行的[Scheduler](../../../tools/perf/engineering/scheduler_lab.py)处理到达、分块prefill、decode、取消和容量预留。它推进真实Python状态，但只模拟长度与逻辑轮次，不执行模型前向，也不将轮次解释为延迟。

## 只看当前空闲页会怎样死锁

页大小2，总容量3页。A与B都输入4、输出2，单条最多需要5个KV位置，即3页。若先给A预填4个位置占2页，再给B预填2个位置占1页，全部页耗尽：

- A要执行decode并写第5个位置，需要再1页。
- B要完成prefill，需要再1页。
- 两者都未完成，不能直接释放现有页。

每条请求单独可放下，并不保证共同增量分配可前进。真实框架可采用预留、lookahead、抢占/重算或显式拒绝等策略，各有代价；不能只检查free>0。

## 实验实现的保守容量策略

对请求r，输入I、输出上限O，按I+O−1个前向消费位置估算：

~~~text
R(r) = ceil((I+O-1)/page_tokens)
sum(active R(r)) <= pool_capacity
actual_used_pages <= sum(active R(r))
~~~

第一次prefill前预留完整R，完成或同步轮次间取消后解除。上述压力例A预留3页，B等待，A完成后B再进入，避免两条半完成请求互相阻塞。这是GPU内部可行性模型，不替代Go业务准入、Token预留或财务账本。

保守预留可能浪费短输出/EOS提前结束的余量，降低并发。只有用实际负载证明有必要，才比较更灵活的lookahead或recompute。改变预留策略时需继续验证最坏长度、OOM、重算质量和取消。

## 调度一轮具体做什么

先按到达时间筛选请求。已ready的decode采用轮转顺序；若存在pending prefill，给它至少保留1个逻辑预算，其他预算用于decode。prefill按到达/id排序，每次推进min(chunk,剩余预算,剩余输入)。

Prefill最后一个位置采样第一个输出；额外decode消费上一个输出并产生下一个。输出上限O=1时，prefill完成即可结束，不额外执行一次decode。测试专门核对这条路径。

每轮在逻辑完成前记录peak_pages_before_completion与reserved_pages_before_completion，检查used≤reserved≤capacity。若先把已生成最后token的请求释放再统计峰值，就可能漏掉同轮短暂超容量。

这里budget计量位置数量，不表示相同GPU成本。一个prefill token与一个decode位置的计算、KV读取和batch效率不同；真实成本模型需要phase/shape数据。调度器与第5章页池也尚未接真实Worker，异步安全不能由本同步实验推出。

## 公平性要声明保证条件

本实验给pending保留预算、轮转decode，并在50组固定种子有限工作负载中检查所有请求完成。它没有证明持续到达、过载或任意资源碎片下无饥饿。

想建立等待上界，需要规定接纳率、最大输入/输出、队列容量、抢占与资源条件。可按年龄提升优先级，或分别设prefill/decode队列与额度，但每项都要验证长短请求的尾延迟。只提升短请求平均值可能牺牲长请求。

输出也会阻塞资源：客户端慢读造成有界队列满时，应按协议停止继续生成并进入取消/安全回收，不静默丢token。队列长度、排队年龄、inflight工作和实际设备停止应分别观测。

## 把策略变成真实实验

先冻结J02的200条120/60/20顺序、hash、输入输出与冷热条件。主baseline使用现有成熟配置，一次只改chunk或容量策略之一，保持GPU、精度、slot、rate与预算。

分别交长/短TTFT、TPOT、共同窗口G、失败/拒绝/pending、峰值显存、逐出/重算与调度CPU。Offered到sent的差距与客户端饱和也要保留。若总体改善却重要长度格退化，候选是否可接受由预登记门槛决定。

Little定律L=λW只在相应稳定边界和统计定义下成立，不能把过载/拒绝/取消混合的某次快照硬套成排队模型。真实实验计划继续保持禁用，CPU轮次报告仅验证状态与容量不变量。
