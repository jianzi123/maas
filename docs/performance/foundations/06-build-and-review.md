# 分阶段实现与评审练习

后续框架应从有确定输入输出的小闭环生长。先建立数学与状态参考，再接真实 Worker 或集群适配器；每次引入新异步边界，都补对应恢复与正确性用例。ADR 是架构决策记录，用于说明背景、候选、取舍与验证条件。下面是实现建议和评审材料，不是本轮启动新框架、部署或 GPU 实验的授权。

## 推理运行时实现路线

| 阶段 | 范围和建议文件 | 可检查完成条件 |
|---|---|---|
| R0 数学与身份参考 | reference、shape_cases、request_binding、单位说明 | 手算 GEMM/Attention/RMSNorm 对齐；mask/GQA/finite/布局边界明确；请求与修订不混淆 |
| R1 确定性调度与内存模型 | scheduler、page_table、retire_queue、fake_worker | 固定到达序列可重放；无超容量分配；取消后不新增提交；refs=0/inflight>0 不复用；重复/旧回包不双释放 |
| R2 获准 GPU Worker 适配 | worker_adapter、completion、device_timing、backend_registry | 与成熟 baseline 比较；正确性先于计时；跨 stream 生命周期有证据；OOM/Worker 故障关闭；准备与稳态分开 |
| R3 框架负载验证 | load_manifest、trace、quality、benchmark_report | 同模型/精度/资源下固定负载；长短/冷热分层；拒绝失败 pending 全保留；质量/取消/显存和批准 SLO 同时成立 |

R1 可以先在 CPU 上控制事件顺序，理解状态问题；它不能证明 R2 的 CUDA 地址、stream 或真实 kernel 正确。R2 单算子快也不等于 R3 请求快。建议先接一种已有成熟执行后端，把调度与内存边界做清，再考虑自研热点 kernel。

## 部署框架实现路线

| 阶段 | 范围和建议文件 | 可检查完成条件 |
|---|---|---|
| D0 纯计划与资源预算 | spec_reader、resolver_port、planner、inventory_model | 相同快照计划确定；来源互斥；原 UID/修订绑定；蓝绿资源总量可解释；缺批准引用不生成执行计划 |
| D1 可恢复协调器与替身 | journal_port、reconciler、fake_resource_executor | 同身份同 payload 幂等，异 payload 冲突；每个 prepare/execute/record 截点重启；ACK 未知不新造身份；旧 owner 不能激活 |
| D2 获准实际适配器 | K8s、发布存储、网关/验证适配 | 真 UID/CAS、耐久提交与窄权限；真实服务集合及启动代次回执；Secret 不入响应；没有真实证明不 Ready |
| D3 生命周期验收 | publish、update、rollback、offline、cleanup 的场景记录 | 发布与固定来源调用关联；回滚新 publication；取消/排空/未知 held 分离；同名新 UID 不误删；历史/权限/重启通过 |

D1 内存 journal 只教幂等，不等于 MySQL 耐久。D2 受控验证也不能替代 D3 的真实发布与业务约束。已有 MAAS-3/MAAS-11 由原负责人实施，后续工作应复用而非重新平行实现其业务内核或共享契约。

## 一次可评审课题应该长什么样

以“J02 下长 prefill 干扰 decode”为例。提交内容应能让其他工程师复核：

1. 写出问题触发条件：固定 J02 序列、hash、到达计划、资源/精度/配置，哪一层 TTFT/TPOT 退化。
2. 附原始时间线与关联数据，证明干扰在运行时关键路径；排除负载发生器饱和、客户端时钟混合和网关拒绝引起的假象。
3. 说明成熟 baseline、单因素候选和预登记门槛；例如只改变 prefill chunk，不同时改 slot、缓存和模型精度。
4. 附每个 shape/长度格的正确性与原始结果，失败/取消/pending 也进入报告。配对 run 才是收益统计单位，不能把同 run 内相关请求冒充独立重复。
5. 给出副作用和否证结果：长请求饥饿、CPU 上升、KV 重算或关键格 SLO 退化会使候选失败。即使结论是“不采用”，也有工程价值。

算子课题同理：先证明热点与占比，再比较成熟 baseline；保留准备、数据搬运和通信。优化阈值、SLO、资源与预算须先批准，现有 +10%/配对建议不自动适用于全部算子。

## 十四道工程题与参考判断

先独立回答，再看下面的解释。答题时要指出状态、所有者与具体证据，不能只写“加锁”“重试”“加监控”。

### 题 1 首 token 从哪里来

输入长度 4、输出长度 3，通常需要几次 prefill 与额外 decode？完整 prefill 的末位置产生第一个输出；不切块时一次 prefill，再两次 decode。分块会有多次 prefill 调度，但不会让所有输出都变成额外 decode。最后一个输出通常不再写 KV。

### 题 2 两种时间线能直接相减吗

Client 的 t=100 和 Worker 的 t=80 来自不同 monotonic clock_scope，能说网络耗时 20 吗？不能。先分别计算各自 scope 内间隔；只有经过明确且可验证的归一化才做跨域时间差，共同 RPS 窗口也不能直接拼接。

### 题 3 六轮调度的峰值页数

第二章 step 2 为什么为 4？A 的 4 个输入加 1 次 decode 已消费位置为 5，按 2/token 页占 3 页；B 预填 1 个占 1 页。生成输出计数不能直接相加当 KV 长度。

### 题 4 68 条能作为平台并发吗

不能。它是虚构普通 KV 公式及显存拆分下的上界，不含真实吞吐、尾延迟和所有业务约束。safe_platform_concurrency 保持 null，需单独批准和验证。

### 题 5 页引用清零后出现迟到写入

只增加 allocation generation 是否足够？不够。它可以拒收旧 host 回包，但无法阻止已提交 kernel 写旧地址。必须在真实设备完成或可靠隔离后复用，并防重复回收入池。

### 题 6 共用半满前缀页能直接追加吗

不能直接写共享区域。先处理写时复制或等价隔离，再追加。核对确切 token、位置、权重/模板和安全上下文；只比较字符串前缀不足以证明可复用。

### 题 7 GEMM 尾部线程能提前返回吗

M=37/N=53/K=29、tile16 时共有 12 block，K 跑两轮，末行/列/K 有效数为 5/5/13。越界线程若在 block barrier 前 return，可能破坏共同同步；应填零、参与屏障，只对最终有效地址写回。

### 题 8 2 乘 5 causal mask 为什么可能错

查询对应绝对位置 3、4 时，应看 [1,1,1,1,0] 与全可见行。左上角三角是另一种位置语义。输出 shape 和 finite 都对，仍可能逻辑错误；需要明确 mask 样本。

### 题 9 Kernel 耗时减半为什么请求只快一点

若它只占串行关键路径 20%，上界约 1.111 倍；实际还有重叠、搬运与队列变化。必须验证暴露占比与 R/E 层，不能将 K 层倍数直接写成平台提升。

### 题 10 发布超时后生成新命令安全吗

若原事务已提交但 ACK 丢失，新命令会扩大副作用。用原 command ID/payload 摘要读回，重复同 payload 返回原结果，异 payload 拒绝。读回仍不可用时保留 unknown，而非猜测失败后自动重发。

### 题 11 两台网关只收到一份回执

不能因为另一台暂不 Ready 就忽略其服务中的旧连接。需按真实服务集合、实例身份/启动代次和新鲜度核验；toy coverage 的 set 相等也不能替代可信回执。

### 题 12 模型下线且 held=140

若在途与未安全回收 allocation 已归零，是否必须退款才能清理？不应退款。资源清理还需 inventory/停止/UID 等证据，但财务未知 held 可以保留，不是 GPU slot 计数。不能改成 actual=0。

### 题 13 老对象删除后同名重建

以原 UID 为归属边界。旧 reconcile 不能删除新 UID 的资源，旧回执不能使新对象 active；历史也不能混在一起。回滚需要新发布身份和当前依赖批准。

### 题 14 Graph 命中率高但 G 下降

检查 capture/padding/准备 CPU 与显存是否挤占 KV，导致逐出、重算或更小 batch。保留 eager 消融但比较成熟主 baseline，报告 fallback 与未完成样本；命中率本身不是优化成功标准。

## 团队学习与交接方式

新人用前三章提交一页手算、一次脚本输出和一段自己的解释；进阶成员用第四、五章交接口草图与至少五个确定故障截点；高级工程师负责评审基线合理性、并发所有权、恢复权限与否证条件。相同材料能成为后续框架的设计输入，不以背术语或测试数量判定能力。

每轮总结按“问题—机制—证据—决定—剩余限制”写，引用提交、原始数据和版本。课堂输出、受控组件验证、真实 GPU/框架和真实平台收益分栏记录。可直接使用[总结模板](../templates/weekly-summary.md)与[目标卡](../templates/optimization-goal.md)。

本轮仅交付教材、教学模型与离线验证。真正实现时，先由 Mika 明确里程碑、负责人和授权环境，再复用现有仓库与已交付内核；不要因完成本课程就自动启动 backlog、下载权重或购买资源。
